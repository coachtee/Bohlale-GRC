## Session 3 — Docker deployment toolkit

Added a second, fully supported deployment path (the VPS/systemd path in `DEPLOYMENT.md` is unchanged and still primary/Docker-free): `Dockerfile` (multi-stage, non-root runtime user, `HEALTHCHECK` against `/health/`), `.dockerignore`, `entrypoint.sh` (waits for Postgres via a real `psycopg2` connection attempt, runs migrations, collects static files, optionally auto-creates a superuser from `DJANGO_SUPERUSER_EMAIL`/`DJANGO_SUPERUSER_PASSWORD` — idempotent, verified live against the real app), `gunicorn.conf.py` (env-driven worker count/timeouts, `preload_app=True`), and `compose.yml` (services literally named `bohlale-grc` and `postgres` per this deployment's requirements, `postgres:16-alpine` with a persistent volume + `pg_isready` healthcheck, joins the pre-existing external network `bohlale-health-staging_private`, `restart: unless-stopped` on both services).

`config/settings.py`'s Postgres block gained `CONN_MAX_AGE`/`CONN_HEALTH_CHECKS`/optional `DB_SSLMODE` (additive, env-driven, doesn't change the VPS path's behaviour beyond enabling connection reuse there too).

A `deployment/` toolkit was written to be genuinely generic (no project name hardcoded except the two literal service-name/network-name requirements in `compose.yml` itself — see `deployment/README.md`'s "Reusing this toolkit" section) — reusable for Bohlale Learn/Health/Notes/future projects by copying the directory and changing `.env`:

- `install.sh` — the one-command entry point (`sudo ./deployment/install.sh`): validates Docker/Compose, creates `.env` from `.env.example` with freshly generated `DJANGO_SECRET_KEY`/`POSTGRES_PASSWORD` if missing, creates the external network/volumes if missing, builds, migrates an existing `db.sqlite3`'s data into Postgres if one is found (dump → migrate → load → rename the original with a timestamp suffix so a re-run doesn't repeat it), starts the stack, and waits for `/health/` before printing a success summary.
- `update.sh` — git pull → backup → tag the outgoing image as `:previous` → rebuild → migrate → collectstatic → restart → health-check.
- `backup.sh` — `pg_dump` (custom format) + a copy of the media volume + a manifest, bundled into one timestamped `.tar.gz`, with age-based retention.
- `restore.sh` — restores the latest (or a specified) backup archive; destructive, prompts for confirmation unless `FORCE=true`.
- `rollback.sh` — retags `:previous` back to the live tag and delegates to `restore.sh` for the matching backup (the backup `update.sh` takes immediately before each deploy corresponds in time to that deploy's `:previous` image).
- `health.sh` — container status + Postgres readiness + `/health/` check, non-zero exit on failure, suitable for cron/external monitoring.
- `_lib.sh` — shared helpers (logging, `.env` loading/creation, Docker/Compose validation, the compose wrapper, health polling) sourced by every script above.

**Verification performed in this sandbox** (no Docker daemon is available here — confirmed via `docker info`/`sudo service docker start`, both fail with a sandbox permission restriction, not a real-environment issue): every shell script passes `bash -n`; `compose.yml` was validated with a real `docker compose ... config` render (using a disposable `.env` with test values, removed afterward) confirming correct YAML, variable interpolation, service names (`bohlale-grc`, `postgres` — exact matches), external-network/volume naming, and that the `DB_ENGINE=postgres` override correctly takes precedence over a plain `.env`'s `DB_ENGINE=sqlite`; the `entrypoint.sh` superuser-creation logic was extracted and run live against the real Django app + a scratch SQLite database, confirming it creates a working superuser (password verified via `check_password`) and is idempotent on a second run. **What was not verified**: an actual `docker build`/`docker compose up` end-to-end run, since no Docker daemon is reachable in this environment — a human (or a session with daemon access) should run `sudo ./deployment/install.sh` once against a real Docker host before relying on this path for a real deployment, the same "verify, don't just document" principle applied to the backup/restore drill in `BACKUP_RESTORE.md`.

### Session 4 — Deployment readiness review

A follow-up review pass over the Docker toolkit (Dockerfile, compose.yml, entrypoint.sh, .env.example, and every `deployment/*.sh` script), on the same Docker-daemon-unavailable sandbox as session 3. Findings:

- **Real gap found and fixed**: `.env.example` ships `DJANGO_DEBUG=True` (correct for its primary audience, plain `manage.py runserver` local dev), but `deployment/_lib.sh::ensure_env_file()` only forced safe values for `DJANGO_SECRET_KEY`/`POSTGRES_PASSWORD` when generating a fresh `.env` for a Docker install — a first-time `sudo ./deployment/install.sh` on a real VPS would have silently gone live with `DEBUG=True` (stack traces/settings exposed on error pages) unless the operator happened to notice and change it themselves. Fixed: `ensure_env_file()` now also forces `DJANGO_DEBUG=False` on first `.env` creation (deployment-script-only change, zero effect on already-existing `.env` files or on local `manage.py runserver` dev, which never calls this function). `deployment/README.md` updated to describe the new behaviour.
- **Confirmed clean**: no hardcoded paths, usernames, or passwords anywhere in the audited files — every credential is env-var driven with no unsafe default (`POSTGRES_PASSWORD`/`DB_PASSWORD` have no fallback and hard-fail via compose's `:?` syntax if unset); `compose.yml` correctly joins the pre-existing `bohlale-health-staging_private` external network, names the Django service exactly `bohlale-grc`, and gives PostgreSQL a persistent named volume (`postgres_data`, confirmed via a real `docker compose config` render); all scripts pass `bash -n`; `docker compose version` in this sandbox is a genuine v2 plugin (v5.1.1) and the compose file uses the modern Compose Spec (no `version:` key), so it's compatible with Docker Compose v2 as required — nothing in the toolkit assumes a specific host OS besides Docker itself being installed, so Ubuntu 24.04 (with Docker's official apt repo, which supports the `noble` codename) works.
- **`install.sh` idempotency confirmed** for the primary "re-run against an already-installed stack" case: `.env` creation, external network creation, and named-volume creation are all existence-checked before acting; `docker compose build`/`up -d` are naturally idempotent. **One narrow caveat documented, not code-changed**: the one-time `db.sqlite3` → PostgreSQL migration step (`migrate_sqlite_if_present`) renames the source file away only after a full success, so a retry after a genuine first-attempt failure partway through (dump succeeded, `loaddata` didn't) would re-attempt the same dump/load rather than resuming — a real but narrow edge case (only reachable once, only on a host migrating a pre-existing non-Docker SQLite install, only on partial failure), left as-is rather than adding transactional rollback across two database engines for a one-time migration path; call out in `DEPLOYMENT_CHECKLIST.md` if this path is ever used.
- **New `DEPLOYMENT_CHECKLIST.md`** written at the repo root: the copy/paste command sequence for a real Ubuntu 24.04 VPS, from bare host through Docker install, domain/TLS (both shared-reverse-proxy and standalone-Nginx branches), secure-cookie cutover, cron backups, a mandatory pre-go-live restore drill, day-2 ops reference, and a final sign-off checklist — distinct from `deployment/README.md` (which explains what each script does) and `DEPLOYMENT.md` (the non-Docker VPS path).

**Still not verified in this pass** (same sandbox limitation as session 3): an actual `docker build`/`docker compose up` end-to-end run. `DEPLOYMENT_CHECKLIST.md` §5 and §11 are what a human (or a session with real Docker daemon access) should run once against a real host to close this out.

## Known issues

- **Rate limiting is per-process, not shared across Gunicorn workers.** `core/ratelimit.py` uses Django's default cache backend (LocMemCache unless `CACHES` is overridden). With `--workers 3` in the systemd unit (see `DEPLOYMENT.md`), the effective limit is roughly `configured_limit × worker_count` per IP, since each worker keeps its own counter. This still meaningfully blunts brute-force/enumeration attempts and requires no new infrastructure (no Redis), consistent with spec §39's "no mandatory Redis" — documented here so a future session doesn't mistake it for a bug. If stricter enforcement is needed later, point `CACHES` at a shared backend (e.g. `django-redis` or Postgres-backed cache) without changing `core/ratelimit.py`'s interface.
- **Spec §49 (Competitive Research) is explicitly a market-research task**, not a software requirement — "conduct structured research into Eramba, CISO Assistant, Vanta, Drata..." This has not been performed and is out of scope for an autonomous coding session; it should be done by a human (or a session with live web research tooling and product-strategy authority) before Version 1.0 is frozen, per the spec's own framing.
- **Spec §48 (Commercial Model)** is explicitly deferred by the spec itself ("Pricing logic will be determined after market research") — no pricing/billing code exists, correctly, since none was requested.

## Assumptions made (documented per working instruction #24)

1. **`organisations` + `tenancy` merged into one app (`tenancy`)** — the spec's suggested module list (§40) lists both `organisations` and `tenancy` separately but §5–§7 describe a single coherent concept (Organisation model, membership, roles, onboarding). Splitting them would create an artificial boundary. `tenancy` owns `Organisation`, `Membership`, invites, the tenant middleware, RBAC helpers, and the onboarding entry point (which then hands off to `journeys` for the guided wizard).
2. **`projects` folded into `journeys` as `OrganisationJourney`** — §5's hierarchy mentions "Projects / Management Systems" under Organisation; §9's PDCA journey and §47's demo scenario describe the same concept (an organisation's instance of implementing a framework). Rather than a duplicate `projects` app, `journeys.OrganisationJourney` is the project/management-system instance (e.g. "NIBS — ISO 27001 Implementation").
3. **Multi-tenancy strategy: row-level, shared schema.** Every tenant-scoped model has an `organisation` FK (or inherits `TenantScopedModel`). No django-tenants / schema-per-tenant, no separate databases. Enforcement: `TenantMiddleware` resolves `request.organisation` from session + `Membership`; `core.base_views.TenantQuerysetMixin`/`get_object_or_404_scoped` on every view filters by `request.organisation`; cross-tenant access attempts return 404. Verified by a tenant-isolation test in every single tenant-scoped app.
4. **Roles are per-membership, not global**, except `Platform Administrator` which is modelled as Django `is_superuser`/`is_staff`. A user can hold different roles in different organisations via `Membership.role`.
5. **ISO/IEC 27001 and other standards content is NOT reproduced verbatim.** The framework seed data uses original, descriptive summaries of clause/domain structure and original guidance text — never copied text from copyrighted standards. Seeded common-control-library names are original category labels, not copied Annex A control text. POPIA is South African legislation (not subject to the same copyright restriction) but content is still an original summary, not a verbatim copy of the Act, and the product is explicit it is not legal advice.
6. **AI provider default is a local, deterministic `MockProvider`** requiring no API key, so the whole product (including the NIBS demo) works fully offline. `AI_PROVIDER=openai_compatible` in `.env` switches to a real OpenAI-compatible HTTP endpoint; Qwen's OpenAI-compatible mode (e.g. DashScope) is reached the same way by pointing `AI_API_BASE` at it.
7. **PDF export uses print-styled HTML (browser "Print to PDF") plus server-side Excel/CSV (openpyxl)**, not WeasyPrint/wkhtmltopdf, to avoid system-level native dependencies that may not be available on arbitrary VPS targets.
8. **Scheduled/background jobs run via a Django management command intended for cron** (`scan_overdue`), not Celery/Redis, per §39's "no mandatory Redis/microservices" instruction. See `DEPLOYMENT.md` §9 for the crontab example.
9. **Electronic sign-off (§16) is natively implemented** as typed-signature + explicit consent checkbox + timestamp + IP + document hash, recorded as an immutable `Signature` record — not integrated with a third-party e-signature provider in v1.
10. **Organisational change-event "AI suggestions" (spec §26) use a deterministic mapping** (`incidents.models.EVENT_TYPE_SUGGESTIONS`) rather than an actual AI call — simpler, free, instant, and just as effective given the mapping is small and well-defined. A human still confirms/reviews.
11. **Registers app owns only the registers without a natural dedicated app** (Interested Parties, Legal & Regulatory, Processing Activities, Training). Risk/Asset/Supplier/Incident/Corrective Action/Audit Findings each already have a first-class Django app with real business logic. The `registers:hub` page aggregates both kinds, plus filtered views for Data Breach Register (incidents with personal info involved) and Audit Findings Register, so the user experiences one coherent "Registers" section.
12. **Rate limiting (spec §45) is cache-based and per-process**, not a dedicated package (`django-ratelimit`/`django-axes`) or Redis-backed store — see "Known issues" above for the multi-worker caveat and the low-cost path to strengthen it later.
